# ADR（E13–E14 个人补充，241880369）

## ADR-1 在已集成系统上复跑，不重做 A/B 集成

- 背景：E12 已完成 A/B 路线集成，E13 只检验系统对非预设输入和故障的处理。
- 决定：从 `origin/main@ee567dd8` 拉出个人分支 `student/241880369/e13-e14`，复用 `run_e11e12.py`、`labs/e11e12`、`labs/e13e14` 和已构建镜像 `course-e11e12:241880369`。
- 理由：避免重复 E12 工作，保证与组级门禁同一代码基线。
- 代价：个人证据建立在组级实现之上；对实现缺陷只能通过修复 PR 处理，不能改验收口径。

## ADR-2 E14 采用四角色容器 + 本机回环端口

- 背景：E14 要求四角色独立进程、可观察日志与故障恢复。
- 决定：使用 `labs/e13e14/compose.yaml`，四容器分别跑 BuildChecker/EChecker/DRAFT/MDFixer，仅绑定 `127.0.0.1:18081–18084`，仅 draft 挂载 Docker socket。
- 理由：进程隔离、最小权限、端口不暴露公网；与教师彩排一致。
- 代价：依赖宿主机 Docker 与共享教学镜像；需自行做 `down` 清理，不能影响其他组。

## ADR-3 报告哈希按“服务侧实际传输文件”核对

- 背景：编排层会写顶层 `incremental-check.json` 作为阶段包装，真实被 MDFixer 消费的是 echecker 服务目录下的报告文件。
- 决定：核对 C1/E14 报告链时，用 `repair.input_report.sha256` 对比 echecker 服务侧 `incremental/incremental-check.json` 的字节哈希；顶层包装哈希单独记录。
- 理由：反映真实传递与消费的字节，避免把包装文件误当被消费报告。

- 理由：两项都可离线、可重复验证，且直接对应门禁的“回滚”和“Secret”要求。
